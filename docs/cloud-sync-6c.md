# 6c 按账号云端存储验收

## 补充审查 · 记录大小与响应 CPU

真实样本由所有者在本机选择并运行 `node tools/record-sizes.mjs "<导出文件路径>"`。每个集合一行，只输出数量、最大密文字节数、超过 64 / 128 / 256 KiB 的数量和最大的五个长度。脚本调用页面实际的信封、gzip 与 AES-GCM 代码，使用临时钥匙。此阶段等待所有者的汇总，以较大的实测值向上取整到 32 KiB 才能确定上限。

| 虚构边界样本（集合均为 meta） | 请求消息数 | 请求字节 | gzip 后加密信封字节 |
| --- | ---: | ---: | ---: |
| 消息数边界 | 200 | 30,604 | 21,734 |
| 字节数边界 | 199 | 262,144 | 213,214 |

`node tools/record-sizes.mjs --synthetic` 可复测这两组样本。样本带用户材料快照、高熵可打印正文、时间戳和一条 256 字节的末次回复。代码限制发送前非空消息的数量和请求体长度，末次回复和本机卡片保存在请求之后；两组测量代表指定场景，不能推导任意已保存文档的数学上界。

### D1 返回后的 1,900,000 字节拆解

同机 Node v24.18.0，`node --js-base-64 tools/bench-sync-cpu.mjs --stages=1`。输入使用 D1 结果的字节数值数组。下表各阶段独立预热计时，数字为五个区间平均 CPU 时间的中位数，单位 ms。它们与完整请求另行测量，不能直接相加。

| 步骤 | 原拉取 | 原备份 | 优化后两条路径 |
| --- | ---: | ---: | ---: |
| D1 数值数组转连续字节 | 8.857 | 8.857 | 2.049 |
| 原生 base64 编码 | 1.159 | 1.159 | 1.159 |
| 拼 JSON | 3.571 | 9.000 | 0.005（仅序列化元数据） |
| 转为响应字节 | 13.889 | 13.889 | 10.417 |
| 已编码字节写入并读完响应流 | 0.038 | 0.038 | 0.038 |

主要成本在字节数组转换和长字符串的遍历、转码。优化保留 D1 BLOB，用目标数组的 `set` 复制，单独转义元数据，直接写入已编码的 base64。分页备份每次只读当前记录或历史的一页，每页最多 4 次同步数据查询，外加会话查找和可能的续期事务。游标带记录与历史序号，任一变化返回 409，设备重新下载；手机在收到完整分页后才生成文件。

原生 base64 下，优化后单条 1.9 MB 的完整推送 / 拉取 / 首段备份分别为 6.27 / 6.45 / 8.16 ms。一条 224 KiB 的对应数字为 1.20 / 1.01 / 1.21 ms。224 KiB 是由虚构样本得出的最低候选值。

### 实现与测量口径

继续在 D1 存 BLOB。1,900,000 字节的密文转成 base64 后，文本本身就有 2,533,336 字节，超过 D1 单行 2,000,000 字节的限制。Worker 优先使用原生 base64 转换；兼容路径解码使用普通循环，编码每次处理 8,192 字节。设备端解码也已去掉逐字节回调。冲突响应只查并返回 `{k,ver}`，测试核对了完整字段集合。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)

`tools/bench-sync-cpu.mjs` 调用真实 Worker 路由，包含会话哈希、请求体读取、JSON 解析、密文转换及响应生成，流式响应读至结束。D1 使用预制结果；SQL 执行、D1 绑定自身的数据转换和网络均未计入。每组预热三次，使用五个至少 180 ms CPU 的采样区间，表内为区间内单次请求平均值的中位数。CPU 计时优先使用当前线程，Node v24.18.0，Intel Core i7-14650HX。免费 Worker 的 CPU 上限为 10 ms，此处采用审查要求的本机 4 ms 目标。[Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)

| 同机改前（ms） | 推送 | 拉取 | 备份 |
| --- | ---: | ---: | ---: |
| 100 × 3,000 B | 26.86 | 12.53 | 12.53 |
| 100 × 29,850 B（接近原推送上限） | 875.00 | — | 422.00 |
| 100 × 28,000 B（原拉取页上限） | 829.00 | 407.00 | 406.00 |
| 1 × 1,900,000 B | 608.00 | 281.00 | 297.00 |

| 改后，启用 V8 原生 base64（ms） | 推送 | 拉取 | 备份 |
| --- | ---: | ---: | ---: |
| 100 × 3,000 B | 1.33 | 2.54 | 2.32 |
| 100 × 29,850 B | 25.50 | — | 73.00 |
| 100 × 28,000 B | 23.50 | 73.33 | 62.67 |
| 1 × 1,900,000 B | 17.09 | 43.60 | 37.40 |

备份样本仅含表中所列当前记录，历史为零。原备份在一个请求里读取整个账号，所以没有固定的单请求字节上限。另一次单独运行 1.9 MB 样本得到 5.67 / 18.36 / 31.17 ms；两次三项均超过目标。

| 候选传输量 | 转换路径 | 推送 / 拉取 / 备份，各自最慢区间的平均值（ms） |
| --- | --- | --- |
| 1 × 256 KiB | 原生 | 2.63 / 6.45 / 6.45 |
| 1 × 128 KiB | 原生 | 1.70 / 3.69 / 3.40 |
| 1 × 128 KiB | 兼容 | 3.17 / 6.03 / 5.22 |
| 1 × 64 KiB | 原生 | 0.52 / 0.78 / 1.26 |
| 1 × 64 KiB | 兼容 | 0.64 / 1.25 / 1.40 |
| 100 × 655 B | 兼容 | 0.74 / 1.12 / 1.58 |

64 KiB 是本机两个转换路径都有余量的候选传输量。若继续整条传输并采用这个单条上限，上轮容量验收中的大聊天将无法同步。另一选择是保留 1.9 MB 单条容量，将单条密文跨请求传输，完整后再做版本校验并写入当前记录；该方案还需验证断点、重试及不完整分段的回收。

复测命令：

```powershell
node --js-base-64 tools/bench-sync-cpu.mjs
node --js-base-64 tools/bench-sync-cpu.mjs --sweep=1
node tools/bench-sync-cpu.mjs --sweep=1
node tools/bench-sync-cpu.mjs --count=100 --bytes=655
```

脚本的 `--worker=路径` 可以指向原提交检出的 `worker/worker.mjs`，用相同的样本复测基线。此阶段 68 项自动测试通过；构建页面 394,109 字节，gzip 124,974 字节。生产迁移和发布均待后续验收。

## 功能核对

| 场景 | 实测结果 |
| --- | --- |
| 首次认领并换设备 | 认领 1 条日期记录、1 条聊天、1 条备忘录。第二台设备登录同一账号后，从导出文件核对了三种记录。草稿复制到原设备的账号专属存储。 |
| 暂不认领、重复认领、30 天清理 | 暂不认领后退出仍能看到原记录；确认认领后换账号，认领提示为 0 次。将测试副本的保留期设为到期，重新打开后原件清除，之后新增的记录仍在。 |
| 两台设备离线写入 | 分别新增的两条备忘录合并成功；同一条备忘录的两次编辑以时间较新的一份为准。 |
| 冲突历史 | 让较新的编辑先上云，较旧编辑留在离线设备。模拟上传历史中断后刷新，在下载的加密备份中用设备钥匙解开该历史版本，核对集合、文档 ID 和原文。 |
| 删除传播 | 把两台测试设备的编辑和删除固定在同一毫秒，编辑先到云端，再同步删除。两台设备导出时该条均消失。旧提交在此项会恢复已删除记录。 |
| 密码与会话 | 改密后另一设备拉取返回 401。输入旧密码时，账号本机库的记录键与内容指纹一致，云端序号变化为 0。新密码可解开原记录，停止同步后用当前密码重新开启成功。 |
| 账号隔离 | 单元测试和浏览器检查使用两个账号。读取结果按会话所属账号返回；带其他账号标识的写入仍归当前会话，另一个账号的版本、序号和内容保持独立。 |
| 配额与用量 | 配额降到 1 字节后，上传返回 413，本机新增的记录仍可导出。恢复配额后上传成功。覆盖、冲突历史和历史清理都纳入字节统计，整批超限回滚。已超额账号仍可同步删除。 |
| D1 与管理页 | 抽查测试账号的有效记录，键均为 43 位编码，密文中未检出测试用中文。管理页的有效条数与 D1 一致，占用字节与备份中当前及历史密文大小之和一致。 |
| 备份期间有改动 | 在读取备份期间新增历史并同时清理旧历史，即使条数、大小都相同，下载也会中断。重试后成功读取一致的备份。 |
